PROTOFORGE
Architecture Pivot &Implementation Roadmap
From a single-protocol RTL generator to an evidence-driven, multi-agent hardware and driver engineering harness
IMPLEMENTATION BLUEPRINT
Scope: uploaded ProtoForge repository, existing I²C harness, PCIe Linux driver expansion, peripheral protocols, multi-agent orchestration, RAG and LoRA.
Core recommendation
Build correctness and evidence infrastructure first. Add specialised agents after the task and source context are explicit. Add model diversity only after the agent workflow is measurable. Fine-tune only after verified training data exists.
No calendar dates are used. The sequence is dependency-based: each phase has a concrete deliverable and an exit gate.
How to use this roadmap
This document is intended to guide implementation decisions, not merely describe a possible end state. Follow the phases in order. A phase is complete only when its exit criteria are met and the result is captured in the repository. Do not treat the phase list as a calendar; the order reflects architectural dependencies.

Important scope distinction
The uploaded repository is an I²C-focused RTL-generation harness. It does not contain an actual PCIe Linux driver or a target device datasheet. The PCIe phase therefore defines the adapter, source-ingestion and verification work; driver-specific code and register semantics must be derived from the actual target repository and hardware documentation.
Executive recommendation
ProtoForge should evolve into an evidence-driven engineering harness that can understand an existing repository, map requirements to source code, inject known faults, coordinate specialist agents, generate small patches, and reject changes that fail independent verification. The main objective is not to make a model appear more intelligent. It is to make the engineering process more structured, observable and testable.
The strongest foundation already exists in the current I²C pipeline: deterministic RTL scaffolding, structural checks, compilation, lint/synthesis, a bus-level testbench, protocol judging, repair attempts and promotion of verified examples. Preserve that working path as a regression benchmark while separating its I²C-specific logic from the harness core.
Recommended critical path
Stabilise the current I²C baseline → introduce domain adapters → build source ingestion and dependency mapping → generalise mutation testing → add specialist agents → add execution traces → add RAG → add multiple local models → implement PCIe and additional protocols → curate data and fine-tune.
1. Product direction and scope
1.1 Intended product
ProtoForge is intended to be a local-first, multi-agent engineering harness for hardware-facing software and RTL. It should accept a repository, specifications and an engineering task; build a traceable representation of relevant requirements and source dependencies; delegate work to specialised agents; generate reviewable patches; and validate those patches using deterministic tools.
Capability
Expected behaviour
Repository understanding
Index source files, symbols, structures, module interfaces, dependencies, tests and build configuration.
Specification understanding
Extract explicit requirements, constraints, register semantics and protocol behaviour.
Fault injection
Create reproducible, labelled specification and implementation mutants.
Agent coordination
Assign separate analysis, mapping, planning, implementation, review and repair responsibilities.
Evidence-backed retrieval
Retrieve relevant source/specification/test material with provenance and version information.
Independent verification
Use compilers, static analysis, simulators, unit tests, emulation and hardware tests where available.
Model specialisation
Route roles to local models and later evaluate task-specific LoRA adapters.
Observability
Show agent activity, model calls, retrieved evidence, patches, findings and verification results.
1.2 Scope boundaries
Software domain: Linux PCIe host-driver analysis and patch generation in C, subject to the target kernel version and device documentation.
Hardware domain: RTL generation and verification for I²C, SPI and UART initially; AXI/APB can follow once the adapter pattern is proven.
Shared infrastructure: task orchestration, repository indexing, dependency graphs, RAG, model routing, evidence store, mutation framework and dashboard.
Out of scope for the first pivot: unrestricted autonomous agents modifying arbitrary files, training foundation models from scratch, and claiming physical hardware correctness from build or simulation alone.
1.3 Engineering principles
Principle
Implementation rule
Verification is authoritative
Agents propose and critique. Deterministic tests and trusted oracles decide whether a candidate passes.
Separate domain logic
I²C, SPI, UART and PCIe implement adapters; the core does not contain protocol-specific assumptions.
Keep changes patch-sized
Prefer targeted diffs to whole-repository rewrites. Every patch must be reviewable and reversible.
Preserve evidence provenance
Every retrieved fact should identify its source, version, file and location where possible.
Keep canonical truth immutable
Store trusted specifications and oracles separately from deliberately mutated inputs.
Make resource use explicit
Models are loaded and scheduled according to available RAM/VRAM; agents do not imply simultaneous model execution.
Measure every improvement
Use fixed benchmarks and ablations to determine whether agents, RAG, model diversity or LoRA actually help.
2. Uploaded repository: current state
The repository currently describes itself as an I²C v1 RTL-generation harness. Its execution path is narrow but useful: a local model proposes an FSM fragment, deterministic code supplies the wrapper and device wiring, structural checks filter invalid output, external tools compile and inspect the design, a fixed testbench evaluates the bus transaction, and a repair loop handles detected failures.

2.2 Important repository-specific findings
agent_core/agent.py hardcodes the I²C specification path, testbench path, protocol parser, top module and I²C judge. This is the primary source of protocol coupling.
The current model path is a single Ollama client. Logical agent roles and model-provider selection do not yet exist as separate concepts.
The README describes the retrieval layer as a small offline few-shot system derived from a known-good I²C oracle, with additional examples promoted only after compile and simulation pass. It is not yet semantic vector RAG.
The Verilog parser is a lightweight interface parser. It is useful for its current restricted contract but is not a general C/HDL abstract syntax tree indexer.
The two modules in devices/ are mock device modules used in the deterministic RTL composition. The I²C testbench supplies the slave-side bus behaviour. Passing that test demonstrates a bounded master transaction against the testbench, not real-world peripheral compatibility.
drivers/README.md states that board-specific C/Linux drivers are not included. No actual PCIe driver source or target device datasheet is in the uploaded project.
The MCP server is not yet an observability layer: it does not provide a complete agent event stream, model invocation history or evidence-linked run timeline.

PHASE 0 — Stabilise the existing I²C pipeline
Objective. Make the current implementation reproducible and testable before introducing architectural changes.
Why this comes here. The existing path is the only working domain and therefore the best regression benchmark. It must remain a trustworthy reference during the pivot.
Implementation work
Fix test discovery. The root-level test_agent_integration.py, test_reported_bug.py and test_structural_gate.py should either become proper tests or move out of pytest discovery. Configure the intended test roots explicitly.
Fix dependency injection in agent_core/agent.py. run_hardware_checks() is called directly; make validation runners injectable so mocked pipeline tests do not depend on installed Verilator/Yosys binaries.
Add tools/environment_check.py to report availability and versions for Ollama, Icarus Verilog/vvp, Verilator, Yosys, Python dependencies and later kernel build dependencies. A missing tool must produce tool_missing, not an LLM repair request.
Freeze a baseline benchmark: model identity, prompt/config, seed, temperature, retrieval state, compiler/tool versions, candidate hashes, first-attempt pass rate, final pass rate, repair count and latency.
Separate generation failure, infrastructure/tool failure, structural failure, compile failure, lint/synthesis failure and protocol failure in the run schema.
Design constraint
Do not interpret repeated zero-temperature generations with the same seed as independent samples. Keep first-pass and post-repair outcomes separate.
Exit criteria
The I²C golden reference passes its applicable structural, compile, lint/synthesis and simulation checks; the intended pytest command has no collection errors; environment failures are classified separately; baseline results are saved with reproducible metadata.
PHASE 1 — Create the domain-independent core
Objective. Remove protocol-specific assumptions from the main execution path while preserving the current I²C behaviour.
Why this comes here. If the orchestrator remains I²C-specific, every new protocol or driver will require invasive changes to the central agent code. Domain boundaries must exist before expansion.
Implementation work
Create core/schemas.py for Task, Requirement, SourceReference, CandidatePatch, ValidationResult, AgentResult and RunEvent contracts.
Create domains/base.py with domain operations such as parse_requirements, index_sources, build_context, generate_candidate, validate_structure, build_and_test, judge and get_mutations.
Create domains/i2c/adapter.py and move or wrap the existing I²C parser, generator, structural checks, testbench runner and judge behind it.
Refactor agent_core/agent.py into a compatibility entry point that selects a domain adapter and delegates execution to core/orchestrator.py.
Keep existing tools/ imports working during migration. Use adapters and wrappers first; move files only after tests confirm behaviour.
Exit criteria
The I²C benchmark runs through the new adapter and produces equivalent verdicts. The central orchestrator contains no hardcoded I²C spec, testbench, address, transaction or judge logic.
PHASE 2 — Build repository ingestion and dependency mapping
Objective. Give ProtoForge a structured model of the repository so it can retrieve code in meaningful units and understand dependencies.
Why this comes here. Fixed-size token chunks lose function boundaries and omit related data structures, callers, registers and cleanup paths. PCIe driver analysis especially needs cross-file context.
Implementation work
Add indexing/repository_scanner.py to identify languages, source roots, build files, test roots, generated files, vendored code and ignore rules.
Add indexing/c_indexer.py using Clang LibTooling/AST or an AST-capable parser. Capture compilation configuration, target kernel headers and relevant preprocessor definitions where possible.
Add indexing/verilog_indexer.py for modules, ports, parameters, instances, state machines and signal dependencies. Keep tools/verilog_parser.py limited to its current narrow interface contract if adequate.
Add indexing/document_indexer.py for Markdown, text and technical PDFs; preserve page/section locations and document version metadata.
Chunk by semantic entities: function, declaration, structure, macro/register block, module, interface, specification section, test and build/configuration unit.
Create indexing/symbol_graph.py and dependency_mapper.py. Capture calls, references, type usage, include relationships, module instances, register references, test coverage and requirement links.
Store file path, symbol, line span, language, content hash, repository commit, build configuration and dependency edges with every chunk.
Design constraint
A task involving one function must not be represented by that function alone. The context bundle should include the dependencies needed to reason about its lifecycle and side effects.
Exit criteria
Given a task naming a function or requirement, the indexer retrieves that function, relevant callers/callees, structures, headers, register definitions, specification sections and tests. The result can be inspected without calling an LLM.
PHASE 3 — Generalise manual bug injection and independent oracles
Objective. Create a reproducible way to test whether ProtoForge can detect known defects in specifications and implementation code.
Why this comes here. Without known injected faults and independent expected outcomes, it is difficult to distinguish real debugging ability from plausible-sounding generation.
Implementation work
Generalise tests/test_oracle_mutation.py into mutations/schema.py, mutation_engine.py, spec_mutator.py, source_mutator.py and mutation_runner.py.
Create per-domain catalogues such as mutations/catalog/i2c.yaml and mutations/catalog/pcie.yaml. Each case needs a stable ID, description, fault location, mutation operation, expected detection, oracle and affected requirements.
Support specification mutants (wrong timing, register offset, reset requirement or interrupt behaviour) and implementation mutants (wrong state transition, missing cleanup, wrong DMA direction or incorrect register access).
Maintain three test classes: correct spec + faulty code; faulty spec + otherwise correct code; and inconsistent spec/code compared against an independent trusted reference.
Keep canonical specifications and canonical test oracles immutable. Place mutated inputs in separate directories and identify every mutant in run metadata.
Record mutation score, escaped mutants, false positives, detected requirement IDs and the exact evidence used by each agent.
Design constraint
Never derive both the mutated implementation and the only expected test result from the same mutated specification. That creates correlated errors and can make a broken implementation appear correct.
Exit criteria
Every seeded mutation is reproducible. The verification framework rejects known-bad variants for the expected reason, and mutation score is reported separately from ordinary test pass rate.
PHASE 4 — Implement specialist agents and orchestration
Objective. Replace the single generate/repair loop with role-specialised agents that share structured task state.
Why this comes here. Decomposition improves reliability by reducing each model call to a bounded responsibility. First prove the benefit of role separation with one model so model diversity is not confused with orchestration gains.
Implementation work
Create agents/base_agent.py and specialist roles: Specification Analyst, Codebase Mapper, Planning Agent, Implementation Agent, Reviewer Agent and Repair Agent.
Create core/task_graph.py to represent dependencies and execution state; create core/orchestrator.py to schedule roles, enforce transitions, bound retries and collect structured outputs.
Use typed JSON contracts for every agent output. Example fields include task_id, role, objective, requirements, source_references, assumptions, findings, proposed_changes, confidence and next_action.
Make the Implementation Agent produce a patch/diff rather than replacing an entire source file. Validate patch paths and reject out-of-scope modifications.
Give the Reviewer the original requirements and independent source context, not merely the implementer's summary. Require every finding to cite a requirement and source location or test result.
Give the Repair Agent concrete review findings and tool diagnostics; do not ask it to vaguely improve the code.
Start with one local model behind all roles. Compare this multi-agent configuration against the frozen single-agent baseline.
Exit criteria
A seeded I²C defect is located, planned, patched, independently reviewed and repaired through separate agent roles. Every transition is represented in structured task state; retry limits prevent infinite agent loops.
PHASE 5 — Add execution traces and the observability dashboard
Objective. Make every run reconstructable: which agent ran, which model it invoked, what evidence it saw, what it changed and why a verification gate passed or failed.
Why this comes here. Multi-agent systems become difficult to debug when activity is visible only as chat text. Tracing should exist before adding model diversity and a larger retrieval pipeline.
Implementation work
Create core/trace_schema.py, trace_serializer.py and event_store.py. Persist run_started, agent_started, model_invoked, retrieval_completed, patch_created, review_finding, tool_started, tool_finished, verification_result and run_finished events.
Record model/provider/version, configuration, latency, token counts where available, retrieved chunk IDs, source hashes, tool versions, patch hash, stdout/stderr references and final gate results.
Create dashboard views for run timeline, agent status, model activity, code diff/evidence, verification output and agent disagreement.
Expose read-only trace and run-inspection methods through mcp_server/server.py. Keep write/patch operations controlled by the orchestrator.
Represent agent reasoning as inspectable decision records: objective, assumptions, supporting evidence, findings, conclusion, rejected alternatives and next action.
Design constraint
Expose concise, evidence-backed decision records rather than raw private chain-of-thought. The useful audit surface is the agent’s assumptions, evidence, conclusions, actions and verification outcomes.
Exit criteria
A completed task can be replayed from its durable trace. An engineer can identify the model used by each agent, inspect its evidence bundle, review the patch and see every validation result without reconstructing the run from terminal logs.
PHASE 6 — Build hybrid, provenance-aware RAG
Objective. Retrieve the most relevant specification sections, source chunks, tests and previous outcomes for each agent task.
Why this comes here. RAG should use the semantic index and dependency graph already created. Otherwise, retrieval results are disconnected text fragments and can omit critical code relationships.
Implementation work
Separate knowledge collections into specifications, source code, verification assets and engineering history.
Implement both lexical retrieval (SQLite FTS5/BM25) and vector retrieval (FAISS or a local vector store). Combine results, then rerank the shortlist.
Apply metadata filters such as domain, language, kernel version, protocol, document type, repository commit and verification status.
Add dependency expansion: when a function is retrieved, consider its structures, callers, callees, register definitions, module interfaces and related tests.
Assemble context bundles with a budget per agent role. The Planner needs requirements and dependency maps; the Implementer needs target code and constraints; the Reviewer needs patch, requirements and independent evidence.
Keep known-good examples and known-failed examples in separate retrieval channels. Label failed code with its exact failure and never present it as a positive example.
Attach provenance to every retrieved item: file/page, symbol/line span, version/hash, retrieval score and verification state.
Exit criteria
For a task on a known driver function, retrieval returns expected source dependencies, requirement sections and tests with source locations. Retrieval precision/recall is measured against a manually labelled query set.
PHASE 7 — Introduce multiple local models and role-based routing
Objective. Allow different specialist agents to use different local models while keeping agent roles and model providers independent.
Why this comes here. Once one-model multi-agent runs are observable and measurable, model diversity can be introduced as a controlled experiment rather than an architectural guess.
Implementation work
Replace direct Ollama calls with models/base_provider.py, ollama_provider.py, model_registry.py, model_config.py and model_router.py.
Configure a model per role. For example, document understanding may use one model, implementation a code-oriented model, and independent review a different model family.
Support fallback and provider errors explicitly. A model-loading failure must be reported as an infrastructure event, not as a source-code defect.
Add a scheduler for model loading/unloading and concurrent inference limits. Begin with sequential calls or limited concurrency; do not assume every specialist model can remain resident simultaneously.
Run controlled ablations: single agent/single model; multiple logical agents/same model; generator + reviewer on different models; specialist roles on different models; then add RAG.
Measure accuracy, first-pass success, final success, unique candidate diversity, false-positive review findings, repair success, latency and memory use.
Design constraint
For a 16 GB RAM / 4 GB mobile GPU development machine, treat simultaneous residency of several models as a constraint. Use a resource-aware queue and sequential model loading unless measurements justify concurrent execution.
Exit criteria
Agent-to-model assignments are configurable, visible in traces and reproducible. A controlled benchmark demonstrates whether model diversity improves verified outcomes over multi-agent decomposition alone.
PHASE 8 — Implement the PCIe Linux driver domain
Objective. Make ProtoForge understand and safely patch an existing Linux PCIe driver, including lifecycle, BAR/MMIO, DMA and interrupt behaviour.
Why this comes here. PCIe driver development has a different code structure and verification toolchain from RTL generation. It should be a separate domain adapter that reuses the central indexing, RAG, agents, trace and mutation systems.
Implementation work
Acquire the actual target driver source, target kernel version/configuration, device datasheet, PCI vendor/device IDs, BAR/register map, DMA capabilities, interrupt model, reset/power-management rules and build instructions.
Create domains/pcie_linux/adapter.py plus specification, generators, validation, mutations and tests subpackages. Encode device facts in versioned manifests; do not let an LLM invent offsets or bit meanings.
Index probe/remove paths, error unwinds, BAR mapping, DMA setup and teardown, IRQ vector allocation/release, reset/recovery, power management, workqueues, locking and concurrency relationships.
Prefer targeted patches to an existing driver over generating a full driver from scratch. Require every change to map to requirement IDs and source locations.
Implement seeded faults around probe cleanup, BAR selection, DMA mapping/unmapping/direction, interrupt setup/teardown, active-DMA removal, reset and recovery.
Build a validation ladder: kernel module build; compiler diagnostics; Sparse and checkpatch; focused unit tests/KUnit; QEMU integration with a suitable emulated device or custom model; physical hardware tests when available.
Report each validation level separately. Build success does not prove runtime correctness; QEMU success does not prove the actual device behaves identically; hardware results require the real device and safe test setup.
Design constraint
This phase cannot be completed from the uploaded ProtoForge repository alone. A target driver repository and authoritative hardware documentation are required before register-level correctness can be established.
Exit criteria
On a real target driver, ProtoForge maps a task to the relevant source and specification, detects selected injected defects, generates a constrained patch, builds it against the specified kernel and passes applicable tests. The evidence trail identifies every limitation.
PHASE 9 — Expand to SPI and UART; then consider AXI/APB
Objective. Demonstrate that the domain interface is reusable across multiple peripheral protocols.
Why this comes here. Once I²C and PCIe have exercised the shared architecture, SPI and UART can confirm that protocol-specific state, timing and testbenches remain isolated within adapters.
Implementation work
For SPI, model CPOL, CPHA, chip-select timing, bit order, frame width, multiple devices, read/write operations and reset/timeout behaviour.
For UART, model baud rate, start/stop bits, parity, data width, sampling points, framing errors, TX/RX behaviour and timeout/reset cases.
Create independent signal-level testbenches and judges. Do not validate only internal FSM state; observe externally visible protocol behaviour.
Reuse the same mutation schema for wrong clock phase/polarity, bit order, missing chip select, incorrect baud, parity errors and framing failures.
Add AXI/APB only after the first three protocols work without changes to the central orchestrator. Treat AXI bursts, handshakes, backpressure and ordering as their own substantial validation scope.
Exit criteria
A new protocol can be added by implementing its adapter, spec parser, generator and verification backend. The core orchestration and trace contracts remain unchanged.
PHASE 10 — Build a verified-data and LoRA specialisation pipeline
Objective. Use ProtoForge’s accumulated verified engineering data to improve selected local models for specific roles.
Why this comes here. Fine-tuning before the harness has trustworthy examples risks teaching the model unverified code, benchmark leakage and incorrect conventions. RAG and fine-tuning solve different problems and should be evaluated separately.
Implementation work
Create training/dataset_builder.py, dataset_validator.py, train_lora.py and evaluate_adapter.py. Store dataset snapshots and training configuration with each experiment.
Build examples from verified code patches, specification-to-requirement mappings, bug diagnosis, compiler/simulation repairs and reviewer findings. Include negative examples only with explicit labels and correct diagnosis.
Deduplicate near-identical examples; remove secrets and irrelevant repository data; track source licences and whether model/dataset use is permitted.
Split training, validation and test sets by repository/device/task family where possible, not merely by random adjacent rows. Prevent the same injected bug or near-identical code from leaking across splits.
Start with one role-specific adapter, such as RTL generation or PCIe code review. Keep the base model fixed during the first experiment.
Compare base/no-RAG, base+RAG, LoRA/no-RAG and LoRA+RAG on the same held-out benchmark. Report quality and resource cost.
Use PEFT/LoRA or QLoRA rather than training a foundation model from scratch. Use a machine with suitable VRAM if the local laptop cannot train the selected model reliably.
Exit criteria
A saved adapter reproducibly improves a defined held-out task over the base model, without lowering performance on critical regression tests. The dataset, split, base model, adapter parameters and evaluation outputs are versioned.

Use stable IDs for requirements, source chunks, mutations and tests. This makes it possible to connect a reviewer finding to an exact requirement, implementation function, injected fault and verification case.
5.2 What “show agent reasoning” should mean
The dashboard should show an auditable decision trace, not raw hidden chain-of-thought. Raw free-form reasoning is not a reliable engineering record. The useful explanation is a compact, evidence-linked account of what the agent was asked to decide, what sources it consulted, what assumptions it made, what it concluded, which alternative it rejected, what action it took and what the tools reported.

A practical local-first implementation is SQLite FTS5/BM25 for lexical search, FAISS or another local vector store for embeddings, and a lightweight reranker. Keep the retrieval interface independent from the selected database so it can be replaced without changing agent code.
6.2 Retrieval flow
1. Parse the task into domain, language, requirement IDs, symbols, error messages and likely subsystem terms.
2. Apply metadata filters before scoring so an I²C example is not retrieved as a PCIe implementation merely because both mention registers.
3. Run keyword and semantic retrieval; merge and rerank candidates.
4. Expand from a retrieved symbol into its relevant dependencies: types, callers, callees, register definitions, module interfaces and tests.
5. Assemble a role-specific context bundle with source references and a context budget.
6. Record every retrieved chunk in the run trace and make the evidence references available in agent outputs.

7. PCIe Linux driver domain: implementation detail
This is the first major software domain to add after the shared harness is working. It should target an existing driver rather than invent a generic PCIe device. Linux PCI device discovery, BAR resource handling, DMA APIs, interrupt allocation and teardown are defined by kernel interfaces, but the actual register map and device lifecycle are vendor-specific.
7.1 Required inputs before code generation
Input
Why it is required
Actual driver repository and commit
Establishes file layout, current coding style, implementation and dependencies.
Target Linux kernel version and configuration
Kernel interfaces and available APIs vary; build compatibility must be explicit.
PCI vendor/device IDs
Identifies the intended device binding and supported revisions.
BAR layout and register map
Prevents invented offsets, sizes, access widths and bit meanings.
DMA capabilities
Defines address width, coherent/streaming use, descriptor format, alignment and transfer constraints.
Interrupt model
Defines INTx/MSI/MSI-X support, vector needs, acknowledgement semantics and teardown.
Reset, power and recovery behaviour
Defines what must happen during probe, error recovery, suspend/resume and removal.
Datasheet or authoritative vendor documentation
Supplies the hardware facts that cannot be inferred from generic PCI APIs.
7.2 Source relationships the indexer must capture
probe()  ├── enable device  ├── request / map BAR resources  ├── configure DMA masks and buffers  ├── allocate IRQ vectors and register handlers  └── initialise device enginesruntime  ├── submit / complete DMA  ├── handle interrupts  ├── coordinate locks, workqueues and state  └── recover from errors / resetremove() / teardown  ├── stop new work and quiesce device  ├── stop outstanding DMA  ├── disable device interrupts and release handlers  ├── unmap / free DMA resources  ├── unmap BAR and release regions  └── disable device
The exact order and cleanup API depend on how the target driver acquired resources and whether it uses managed APIs. The agent must inspect the actual code and kernel version rather than applying a fixed teardown template mechanically.

9. Training, evaluation and LoRA
9.1 What should enter the dataset
Verified successful task: task description, requirements, relevant context, generated patch, review outcome and independent verification record.
Verified repair: failing patch, exact diagnostic, reviewer finding, corrective patch and tests that demonstrate the fix.
Bug diagnosis: mutated input, expected defect, correct root-cause explanation, source evidence and oracle result.
Negative example: retain as a labelled failure and retrieval/debugging resource; do not silently mix it into positive code-generation targets.
9.2 Dataset safeguards
Only include examples with recorded verification status and reproducible source hashes.
Deduplicate near-identical patches and prompts; track the repository/device/task family from which each example came.
Separate training, validation and test sets by repository, device or bug family where possible to reduce leakage.
Remove secrets, credentials, proprietary material without permission and unrelated user data; record applicable source and model licences.
Keep a frozen held-out evaluation set and do not use its failures as training examples until that evaluation cycle is closed.
9.3 RAG versus LoRA
RAG
LoRA
Provides current external facts and source evidence at inference time.
Adapts model behaviour using curated examples.
Can incorporate a new datasheet or code revision by re-indexing.
Requires a training and evaluation run to change the adapter.
Supports citations and provenance when retrieval is recorded.
Does not automatically explain where a learned fact came from.
Useful for device-specific and kernel-version-specific knowledge.
Useful for recurring task patterns such as structured patching or review.
Use RAG for factual, versioned knowledge that must remain traceable. Use LoRA for repeatable task behaviour that has demonstrated value across many verified examples. Do not expect LoRA to memorise every register map or replace current documentation.

11. Expected end-to-end harness behaviour
When the architecture is complete, a task such as “find and fix the incorrect DMA cleanup path in this PCIe driver” should execute as follows:
1. Ingest the repository and identify the target kernel version, build configuration and driver symbols.
2. Extract the relevant requirements from the datasheet and Linux DMA documentation, retaining source references.
3. Map the DMA submit, completion and cleanup functions to their structures, callers, IRQ paths and tests.
4. Plan the smallest patch that addresses the named defect and list the validation cases it must pass.
5. Generate a reviewable patch against the original source; do not replace unrelated files.
6. Have an independent reviewer inspect the patch against requirements and source evidence.
7. Run deterministic build, static analysis, unit/integration and mutation tests appropriate to the domain.
8. If a gate fails, route the exact diagnostic and evidence to the repair agent, then repeat review and verification within a bounded retry budget.
9. Accept only when all required gates pass; label the achieved verification level accurately.
10. Persist the patch, evidence, trace and evaluation result. Promote the example to training data only after dataset validation.

ProtoForge should be judged by the quality of its evidence-backed engineering outcomes: correct requirements, relevant code context, minimal patches, independent fault detection, reproducible verification and traceable decisions.
